# 2. Краткий вердикт

Проект в целом запускается и отображает сайт, но текущая backend-архитектура небезопасна для публичной эксплуатации.

Главные риски:

1. Публичная запись в каталог без авторизации.
2. Stored XSS через `item.image`.
3. Публичный Telegram proxy без серверного rate-limit.
4. Неатомарный счётчик заявок в Cloudflare KV.
5. Дублирование заявок после частичной ошибки multipart.
6. Прикреплённые файлы не очищаются после успешной заявки.
7. Двойной submit создаёт два запроса.
8. Пользовательские данные отправляются в Telegram с `parse_mode: HTML` без экранирования.

До исправления первых трёх пунктов production Worker не рекомендуется считать защищённым.

# 3. Критические проблемы

## P0-1. Публичная запись в каталог без авторизации

**Файл:** `worker/src/index.ts`

**Места:** строки 61–87, 157–161.

`POST /api/catalog` принимает как полную замену каталога:

```json
{"items":[...]}
```

так и добавление:

```json
{"action":"add","item":{...}}
```

Проверки авторизации, API-токена, Cloudflare Access, разрешённого администратора или `Origin` нет.

### Воздействие

Любой HTTP-клиент может:

- удалить весь каталог;
- добавить произвольные работы;
- заменить описания, категории и URL изображений;
- записать чрезмерный JSON;
- подготовить stored XSS через поле `image`.

CORS не является механизмом авторизации: запрос можно выполнить через `curl` или серверный скрипт.

### Рекомендация

Предпочтительный вариант:

1. Оставить публичным только `GET /api/catalog`.
2. Убрать публичный `POST /api/catalog`.
3. Запись выполнять через:
   - Cloudflare Access;
   - отдельный admin Worker;
   - Telegram-бот с проверкой разрешённого `chat_id`;
   - защищённый `wrangler kv put`/seed-процесс.

Токен администратора нельзя встраивать в статический frontend.

## P0-2. Stored XSS через `item.image`

**Файл:** `scripts/catalog.js`

**Места:** строки 36–53.

`name` экранируется через `escapeHtml`, но `image` вставляется в HTML напрямую:

```js
var imgHtml = img
  ? '<img src="' + img + '" alt="' + name + '" loading="lazy">'
  : ...;
```

### Подтверждение

В браузере на detached DOM-шаблоне проверено, что значение вида:

```text
x" onerror="window.__catalogProbe=1
```

превращается в HTML с реальным атрибутом `onerror`.

### Цепочка эксплуатации

1. Атакующий добавляет item через публичный `POST /api/catalog`.
2. Вредоносный item сохраняется в KV.
3. Посетитель открывает `works.html`.
4. `catalog.js` вставляет `image` через `innerHTML`.
5. Код может выполниться на origin GitHub Pages.

### Рекомендация

Нужно исправить оба уровня:

1. На Worker — валидировать URL изображения.
2. На клиенте — не собирать карточку через HTML-строку.

Использовать DOM API:

```js
const imgEl = document.createElement('img');
imgEl.src = validatedImageUrl;
imgEl.alt = item.name || '';
imgEl.loading = 'lazy';
```

Разрешать только:

- относительные пути `images/...`; либо
- allowlist доверенных CDN;
- ограниченный набор расширений;
- допустимую длину URL.

## P0-3. Публичный Telegram proxy позволяет спамить владельцу

Клиентское ограничение через `localStorage` не является защитой.

### Возможности злоумышленника

- отправлять произвольные сообщения в чат владельца;
- расходовать лимиты Telegram и Worker;
- отправлять до 5 файлов на запрос;
- генерировать номера заявок;
- создавать flood и мешать настоящим клиентам.

### Рекомендация

Добавить:

1. Cloudflare Turnstile.
2. Серверный rate-limit по IP через Cloudflare Rate Limiting, Durable Object или другой согласованный механизм.
3. Honeypot.
4. Ограничения длины всех полей.
5. Серверную валидацию типов и размеров файлов.
6. Allowlist `Origin` как дополнительную, но не единственную защиту.
7. Разделение endpoint’ов заказов и отзывов.

# 4. Высокий приоритет

## P1-1. Гонка в счётчике заказов

**Файл:** `worker/src/index.ts`, строки 27–32.

```ts
const raw = await env.CATALOG_KV.get(COUNTER_KEY);
const current = raw ? parseInt(raw, 10) || 0 : 0;
const next = current + 1;
await env.CATALOG_KV.put(COUNTER_KEY, String(next));
```

Это неатомарный read-modify-write.

Два одновременных запроса могут прочитать одно значение и получить одинаковый номер.

### Рекомендация

Использовать:

- Durable Object с последовательным инкрементом;
- D1/SQLite с транзакцией и `AUTOINCREMENT`;
- либо другой механизм атомарной координации.

`Date.now() + random suffix` допустим только как временный компромисс, если последовательная нумерация не обязательна.

## P1-2. Fallback может отправить одну заявку дважды

**Файл:** `order.html`, строки 288–307.

**Worker:** `worker/src/index.ts`, строки 120–141.

Сценарий:

1. multipart-запрос отправляет текст;
2. Worker успешно отправляет текст в Telegram;
3. один из файлов не отправляется;
4. Worker возвращает HTTP 400;
5. клиент повторяет отправку обычным JSON;
6. в Telegram появляется второе сообщение и новый номер заявки.

Такая же проблема возникает при timeout после фактического принятия сообщения Telegram.

### Рекомендация

Добавить `request_id`/idempotency key:

- клиент отправляет уникальный ID заявки;
- Worker сохраняет состояние обработки;
- повтор с тем же ID не создаёт новую заявку;
- частичная ошибка возвращается явно;
- автоматический fallback после неопределённого результата не выполнять.

## P1-5. Пользовательские данные отправляются в Telegram как HTML

**Файл:** `worker/src/index.ts`, строки 37–42, 104, 124.

Используется:

```ts
parse_mode: 'HTML'
```

но имя, описание, контакт, цвет, количество и имена файлов не экранируются.

### Воздействие

- `<`, `>` и `&` могут сломать отправку;
- Telegram может вернуть `can't parse entities`;
- заявка не попадёт владельцу;
- пользовательские данные могут менять формат сообщения.

### Рекомендация

Предпочтительно убрать `parse_mode: 'HTML'` и использовать plain text.

Если HTML необходим, экранировать пользовательские значения на сервере:

```text
& → &amp;
< → &lt;
> → &gt;
```

# 6. Accessibility, UX и производительность

## Формы

- большинство `<label>` не имеют `for`;
- `quantity` использует `type="text"` вместо `number`;
- отсутствуют `maxlength` и `minlength`;
- нет inline-ошибок около полей;
- нет `aria-live` для статусов отправки;
- нет loading-состояния submit-кнопки;
- рейтинг звёздами не доступен с клавиатуры.

## Навигация и модалки

- отсутствует skip-link к `<main>`;
- мобильное меню не возвращает фокус на кнопку;
- нет `aria-controls`;
- lightbox не объявлен как `role="dialog"` и `aria-modal="true"`;
- нет focus trap;
- после закрытия lightbox фокус не возвращается к исходному элементу.

## CSS и анимации

В `styles/main.css` много `transition: all`. Лучше указывать конкретные свойства.

`prefers-reduced-motion` отключает только часть анимаций. Нужно отключить декоративные постоянные анимации для пользователей, выбравших reduced motion.

`overflow-x: hidden` может скрывать реальные переполнения вместо исправления причины.

## Изображения и загрузка

Каталоговые изображения создаются без явных `width`/`height`, что может приводить к layout shift.

Стоит добавить preconnect для Google Fonts и использовать стабильные размеры изображений.

- unauthenticated catalog POST → `401/403`;
- malformed JSON → `400`;
- oversized body → `413`;
- invalid schema → `400`;
- malicious image URL → rejected;
- concurrent counter → unique values;
- duplicate `request_id` → no duplicate order;
- Telegram special characters → successful plain-text delivery;
- partial file failure → explicit status.

### Browser

- один submit → один POST;
- двойной submit → один POST;
- вложение очищается после success;
- ошибка сохраняет поля;
- malicious catalog item не создаёт event handler;
- lightbox закрывается по ESC и возвращает фокус;
- рейтинг работает с клавиатуры;
- responsive 375/1920.

# 9. Что не следует делать

- Не считать CORS защитой от записи.
- Не хранить admin token в frontend JavaScript.
- Не использовать `innerHTML` для URL и данных из KV.
- Не полагаться только на localStorage rate-limit.
- Не повторять заявку после неопределённого результата без idempotency key.
- Не считать TypeScript-интерфейс runtime-валидацией.
- Не менять лимиты Telegram без проверки актуальной документации.
- Не объявлять проект полностью безопасным только потому, что `node --check` и Python compileall проходят.
- **Не переходить к следующему этапу без коммита и push текущего.** Каждый завершённый этап: `git add -A && git commit -m "..." && git push origin main`. Проверять remote tracking (`git log --oneline origin/main -1`) — push мог вернуть silent 403.
